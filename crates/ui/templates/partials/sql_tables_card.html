{# The Tables panel's left-hand card (#842, redesigned flat #1238): *Reads from* — one row per `relatedArtifact[type=depends-on]`, resolved the same way `$sql-run`'s own graph walk resolves them (`crate::resolve_table_reference`) — and *Used by* — other Libraries and SQL Export jobs that depend on this one (`sql_libraries::used_by_artifacts`/`used_by_exports`). Both are read-only lists except *Reads from*'s own *Add table*/*Remove* mutations. Rendered three ways, all built by `crate::build_tables_card` from one `crate::TablesAnalysis` so none of them can disagree about what is declared or resolved — mirrors `sql_parameters_card.html`'s own three-way split exactly: - The page's own inline render (`oob: false`, `data_document: None`). - The `/run` fragment's OOB companion (`oob: true`) — only when the freshly computed `tables_sig` differs from what the browser posted (`crate::sql_library_run`'s own comparison, #842/NF1): editing Details (adding/removing/relabeling a dependency) re-resolves this card; nothing else on the page does. - The `document` endpoint's own `HX-Request` response (`oob: false` — the request's own `hx-target="#lib-tables"` swaps this element directly): `data_document` carries the updated Details JSON on a successful `add-table`/`remove-table`, applied through `sql-library-panels.js`'s own `host.setDoc()`, exactly like `#lib-params`. *Reads from*/*Used by* are each a flat `ul.lib-tables__list` of `li.lib-tables__row` (#1238) — never a data table, so the card grows no horizontal scrollbar at any width; each row wraps its own alias, target chip/link, and (for *Reads from*) its own *Remove*/*Declare* action. *Remove* is a real `type="submit"` icon button (`icons/x.svg`, `aria-label="Remove {alias}"`) — `form="lib-editor-form"` and `formaction="{{ document_href }}"` — so it works with no JavaScript at all: a plain submit posts the whole document to the `document` endpoint, which re-renders the entire page with the mutation applied and nothing saved. With JavaScript, its own `hx-post`/`hx-target="#lib-tables"`/ `hx-swap="outerHTML"` intercepts that same submit and swaps only this card. #842/04: `unknown_rows` — tables the SQL reads that no dependency declares — render after every resolved `rows` entry, each with its own *Declare {name}* button. *Declare* is never a submit (`type="button"`, `data-declare-table`): with JavaScript, `sql-library-panels.js` fills the always-visible add row's alias field with that row's own name and focuses its search field (`sql-library- panels.js`); without it, `crate::build_tables_card` already pre-fills the *first* unknown table's own name into that same alias field — the only affordance a no-JS visitor has, since the add row carries no open/closed state of its own to toggle. `.toolbar__count` above still counts only `rows` — the *declared* dependencies — never `unknown_rows`. The add row (#1238) — search, alias, *Add* — sits below the list, always visible (also when the list is empty), outside any disclosure: the combobox's own `legend`/hint are visually hidden from this card's own CSS (`.lib-tables__add`) rather than by editing the shared `combobox.html` macro, and the only help text is the one `field__hint` line after the row. #} {% import "partials/combobox.html" as combobox %}
