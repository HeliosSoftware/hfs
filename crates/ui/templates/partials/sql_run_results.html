{# The `$sql-run` preview (#752, generalized across the three SQL on FHIR playgrounds in #839): the results card and its failure notice, written once here and shared by View Definitions, SQL Queries, and SQL Views. Each caller supplies its own "surface" — `run_href` (its `POST …/run` fragment endpoint), `form_id` (the id of the `
` its editable fields live in), `heading_key`/`failed_key` (its i18n keys), and an optional `export_href` — rather than this partial hardcoding one page's ids, URLs, or catalog keys. Rendered nested as a template field for each page's own initial render (`fragment: false` — `{{ run_results.render()?|safe }}`), and directly as the whole response of that page's own `/run` fragment endpoint (`fragment: true`). `fragment` only toggles the `hx-swap-oob` attributes below and whether the `Empty` arm's own load trigger applies (it never fires from a fragment endpoint, which always ends in `Success` or `Failure`); the table markup itself (the `Success` arm) lives in exactly one place. `part` (`RunPart`) selects which half a render emits: `Both` (fragments and View Definitions) writes `#run-notice` then the results markup; `Notice` and `Results` write one half each, so the Library pages can place `#run-notice` inside the SQL card and the results after the tables panel. Every arm below wraps its notice in `part.notice()` and everything else in `part.results()`. `#run-notice` is always present, in both modes, whenever the render includes the notice half: - Empty on success, so a fragment response clears a previous failure. - Carrying the surface's own `failed_key` message on a run or parse failure. When the message names the 1-based line of a `$sql-run` parse error (`sql_views::extract_error_line`), the notice also carries `data-error-line` for the editor to tint. - On its own, page-mode-only `Empty` arm: no results have reached the server yet, so this element also carries the *initial* load request — `hx-trigger="load"`, `hx-include` naming the surface's own form (`#{form_id}`) — run once against whatever the editor currently holds, including a "Create New" starter document. On View Definitions the element sits outside that form; on the Library pages it sits inside it. In fragment mode, `#run-notice` is the `hx-post`'s own swap target, so it never carries `hx-swap-oob` — the response's non-OOB content already lands there. Two more elements do ride their own `hx-swap-oob="outerHTML"` there: - `#run-results` (the results card) on success, and is entirely absent on failure — the client's previous table is left untouched. - `#run-results-meta` on failure only, relabelling the untouched table's meta to "last successful run" (`vd-results-stale`). On success the meta travels inside the `#run-results` card instead, so the two never target the same swap. The `.run-busy` status line (#1750) is `hidden` markup that busy.js reveals while any preview request is in flight (`data-busy-region` on the triggers). It lives inside the card's tools in `Success` and inside the empty `#run-results` placeholder elsewhere, so at most one exists in the document: each fragment response swaps the one it replaces. Page mode renders `#run-results` with the identical id and no OOB attribute — there is nothing to swap into on a hard navigation — so a later fragment response's OOB target already exists in the DOM. htmx only swaps an out-of-band element into an id that already exists on the page — an OOB response with no matching target is silently dropped, by design for the failure/meta case. For `#run-results` itself that is a problem exactly once: the very first live run of a session that has never rendered a table (`Empty`, and page-mode `Failure` — both mean nothing real has appeared yet).
