  # MongoDB reindex benchmark for issue #1403

  This protocol measures the deferred MongoDB reindex rebuild that follows a
  `$bulk-submit` fast-load import (`HFS_BULK_SUBMIT_DEFER_INDEXING=true`, the
  default since #946). It exists because the release-matrix full-corpus
  import (`MANUAL_TESTING_MATRIX.md` §7, 18,955,865 resources) took 9 h 10 m
  to ingest and 17 h 16 m to rebuild on run 17 (2026-09-19/20) — nearly twice
  the ingest — and reproducing that at full scale for every candidate change
  is too slow to gate a PR on. Named after the precedents
  [`docs/postgres-reindex-benchmark.md`](postgres-reindex-benchmark.md) and
  [`docs/deferred-reindex-coordination-benchmark.md`](deferred-reindex-coordination-benchmark.md).

  This is a docs-only scaffold (`PR-docs`, #1403): it fixes the protocol
  before any *gated* arm has run (the tooling smoke tests, SMOKE-0 and
  SMOKE-1, run first), with the results tables in §8 empty. Rows are
  **appended** as each PR's arms are judged — see §8 for exactly which PR
  adds which row — and this file is never rewritten to fit a new one. The
  full design is #1403's approved design (spec and design sections, merged
  with PR0); the measurement detail behind every number here is design
  section S4 (`S4-measurement.md`, kept locally by the maintainer, not in
  this repository).

  ## 1. Scope, and why OBS-26

  The bench never imports the full 18.96 M-resource corpus. Two real files
  carry the measurement instead:

  - **`manifest-obs26.json`**: the first 2,000,000 Observations of the
    corpus (`Observation.part00`–`part04`, byte-identical prefixes of the
    corpus's `Observation.ndjson`) plus `Procedure.part00` (400,000
    resources) as an in-run control. 2,400,000 resources total.
  - **`manifest-provenance.json`**: the corpus's full `Provenance.ndjson`
    (11,704 resources), used only for the byte-cap arms (`P2a-0`/`P2a-cap`)
    and the PR3 memory arm (`P3-prov`), because Provenance is the type whose
    pages are large enough (~108 KB/resource) to matter for a byte cap.

  Why Observation: on run 17 it was 7.70 M of the 18.96 M resources but
  13.2 h of the 17.3 h rebuild (76.5%), while every other type ran at
  760–800 resources/s. OBS-26 is the first 25.97% of that same walk, in the
  same patient-clustered order, so the bench reproduces run 17's Observation
  mechanism at a fraction of its wall time. The miss mechanism is per active
  type, and the working set is that type's random slice, which grows
  linearly with the walked fraction — so the bench scales the **configured
  cache in bytes**, not a rounder nominal figure, keeping run 17's
  slice-to-cache ratios intact:

  | Quantity | Run 17 (7.70 M Obs) | OBS-26 (2.00 M Obs, C_bench0) |
  |---|---|---|
  | Configured cache | 7,671,382,016 B (7.145 GiB) | 1,992,294,400 B (1,900 MiB) |
  | C_eff (0.8 ×, the WiredTiger eviction target) | 6.137e9 B | 1.594e9 B |
  | Today's walk, end-of-type slice (22.5 GB × N/7.70 M) | 22.5e9 B, ratio 3.67 | 5.84e9 B, ratio 3.66 |
  | Id walk, residual (5.98 GB × N/7.70 M) | 5.98e9 B, ratio 0.97 | 1.55e9 B, ratio 0.97 |
  | Resources region the id walk fetches at random (1,302 B BSON average) | 10.0e9 B, ratio 1.63 | 2.6e9 B, ratio 1.63 |
  | Fixed terms (token/display group tails ≈100 MB, internal pages) | ≈1.6% of C_eff | ≈6% of C_eff (slightly pessimistic for the id walk) |
  | OS page-cache headroom beside mongod (RSS ≈ 1.68 × cache in run 17) | ≤ 2.7e9 B against 22.5e9 B (0.12) | 3,840 MiB cap − ≈3,192 MiB RSS ≈ 0.68e9 B against 5.84e9 B (0.12) |
  | Swap | yes (run 17 exhausted 4 GiB of it) | impossible (`--memory-swap` = `--memory`) |

  `--wiredTigerCacheSizeGB 2` (a rounder nominal figure) would instead give a
  today's-walk ratio of 3.40 and an id-walk residual ratio of 0.90 — enough
  drift that B1-s, the half-cache probe, and the sizing rule would read
  optimistic, and Gate 0 (which judges only B0-s) could not catch it. The
  bench reproduces the cache *mechanism*, not the swap; only T3-full (§7.13)
  measures on the swap-prone VM.

  Excluded from this protocol, and covered elsewhere: the full
  18.96 M-resource corpus (`MANUAL_TESTING_MATRIX.md` §7 — see "T3-full" in
  §7.13 below, one confirmation run only); the all-features workspace release
  build (this change is R4 + MongoDB only); PostgreSQL and Elasticsearch
  reindex behaviour
  ([`docs/postgres-reindex-benchmark.md`](postgres-reindex-benchmark.md),
  [`docs/deferred-reindex-coordination-benchmark.md`](deferred-reindex-coordination-benchmark.md)).

  ## 6. Metrics

  Full definitions live in design section S4 §4.9 (kept locally by the
  maintainer). The ones that appear in every results row:

  - **Walk ms/resource** (per type): the walk block's wall time (from the
    type starting to its id phase finishing, once that line exists, or to
    the type finishing today) divided by the resources it walked.
  - **Quartile rate, Q4/Q1**: the walk block is cut into four quarters by
    cumulative inserts (matching how run 17's own decay was quantified);
    Q4/Q1 close to 1.0 means the type never slowed down. Run 17's
    Observation was 0.317 (Q1 341 resources/s, Q4 108 resources/s).
  - **bm KB read/written per row, miss ratio, iowait cores**: from mongod's
    FTDC diagnostic data — the same source run 17's numbers came from.
  - **si KB read into cache / row**: the `search_index` collection's own
    cache-read bytes per inserted row, from `collStats`, separating index
    locality from the resource-fetch cost the id walk (PR1) adds.
  - **fetch server ms per page (p50/p95)**: from the mongod slow log
    (`slowms 0` during the rebuild), classified by index hint and sort so a
    boundary probe or a catch-up round query is never mixed into the
    id-walk figure.
  - **HFS peak memory, foreground p99**: process RSS/private-bytes samples
    and a background read-only probe against the live server, so a
    candidate that speeds up the rebuild by starving foreground traffic is
    caught.
  - **Correctness**: `errorCount 0`, `processed == total`, a per-resource
    census hash and a sample-document hash equal to the reference run, and
    (for the CU arms) verification by search after concurrent writes during
    the walk.

  ````markdown
  **Catch-up in write-free arms.** A type nobody writes to during its walk
  is written exactly once: in OBS-26 both types are "old" at their own
  `t0`, so every resource goes to the id phase and the catch-up rounds walk
  0 — hence G1.6's exact `processed == total`. This is V12: a write-free
  arm whose floor is not `newest_live + 1 ms`, or whose round 1 walked
  anything, is INVALID and escalates.
  ````

  ````markdown
  # Sizing MongoDB for a bulk fast-load import

  This applies to a `$bulk-submit` import of millions of resources on
  MongoDB with `HFS_BULK_SUBMIT_DEFER_INDEXING=true` (the default since
  #946). Under that mode, ingestion skips search-index writes, and one
  deferred rebuild indexes every resource type after each manifest
  finishes — on MongoDB, that rebuild is most of the import's wall time.
  Run 17 (2026-09-19/20, 18,955,865 resources) took 9 h 10 m to ingest and
  17 h 16 m to rebuild; see
  [`docs/mongodb-reindex-benchmark.md`](../mongodb-reindex-benchmark.md)
  for the measured mechanism and the ongoing fix (#1403).

  ## What sets the speed

  The rebuild writes one resource type at a time, walking it and writing
  the `search_index` (and `search_index_contained`) rows for every
  resource. Every index key that **contains** a resource id is inserted
  where that id sorts: client-supplied ids (for example Synthea's UUIDs)
  are random, and server-assigned ids are time-ordered UUIDv7. **The
  effective WiredTiger cache is about 80% of `--wiredTigerCacheSizeGB`** —
  that is WiredTiger's own eviction target (it keeps the cache near 80%
  full), so that is what the working set has to fit in.

  On run 17, Observation (7.70 M of the corpus's 18.96 M resources) took
  13.2 of the 17.3 rebuild hours, while the types before it averaged
  ~760 resources/s and those after it ~800/s, at cache-resident speed.
  **The number to size against is one type's random slice of the indexes,
  not the whole `search_index` collection.** A type whose slice fits the
  effective cache runs at that resident speed regardless of how large the
  rest of the collection is; a type whose slice does not fit decays as its
  rebuild progresses.

  ## The sizing rule

  ```
  wiredTigerCacheSizeGB ≥ (k × M + 1) / 0.8
  ```

  `M` is the millions of resources in your deployment's largest resource
  type (usually Observation for a clinical corpus); `k` is gigabytes of
  cache per million resources of that type, measured for the reindex code
  actually running. This section is written so a later, smaller `k` can be
  **added** below without rewriting the rule or this paragraph.

  ### Before the id-order walk (0.2.x and any build predating #1403's PR1)

  **`k ≈ 3 GiB/M`** (estimated: the upper end of run 17's 20–25 GB random
  slice ÷ 7.70 M Observations ≈ 3 GiB per million). Applied to this
  project's own 18.96 M-resource release corpus, whose largest type
  (Observation) is 7.70 M resources:

  ```
  (3 × 7.7 + 1) / 0.8 = 30.125 GiB cache
  ```

  which needs a container memory cap (see "Containers" below) of about
  60.25 GiB (61,696 MiB) just to keep that one import's Observation phase
  resident. This is usually impractical; below it, expect the rate to
  decay through the largest type the way run 17 did — see
  [`docs/mongodb-reindex-benchmark.md`](../mongodb-reindex-benchmark.md)
  for the measured decay curve (run 17's Observation rate fell from
  341 resources/s in its first quarter to 108 in its last).

  ### With the id-order walk (from #1403's PR1 onward)

  *Not yet published.* Once arm `B1-s` (and, if it also passes, the
  half-cache probe `B1-s-1G`) has run,
  [`docs/mongodb-reindex-benchmark.md`](../mongodb-reindex-benchmark.md) §8
  records the sizing gate's verdict, and this section is updated with the
  measured constant, computed as:

  - if only `B1-s` passes: `k = 0.8 × C_bench_GiB / 2.0`;
  - if the half-cache probe `B1-s-1G` passes too: `k = 0.8 × (C_bench_GiB /
    2) / 2.0`;
  - if Gate 0 recalibrates the bench cache, `k` changes with it.

  A provisional value is never published here before it is measured. If
  `B1-s` itself fails its gate, this section keeps the 0.2.x rule above for
  that release.

  ## Containers

  Always pass `--wiredTigerCacheSizeGB` explicitly. MongoDB's own default
  is 50% of (container RAM − 1 GiB); run 17's 15.3 GiB VM defaulted to
  7.67 GB, which is why its Observation phase decayed instead of erroring —
  nothing enforced the rule above.

  Cap the container's memory so the host's page cache cannot mask a miss
  and the container cannot swap into slower storage:

  ```bash
  docker run --memory <M>m --memory-swap <M>m mongo:7.0 \
    --wiredTigerCacheSizeGB <C>
  ```

  with **`M = C + max(1.5 GiB, C)`, rounded up to the next 64 MiB.** In
  MiB: `M_MiB = ceil((C_MiB + max(1536, C_MiB)) / 64) × 64`. Example: a
  1,900 MiB cache gets 3,840 MiB of container memory — the exact
  configuration [`docs/mongodb-reindex-benchmark.md`](../mongodb-reindex-benchmark.md)'s
  own bench measures under.

  Keep other large containers off the same VM/host during the import:
  device and iowait counters are host- or VM-wide, not per container, so a
  second `mongod` (or any other memory- or disk-heavy process) contaminates
  every measurement you take of this one.

  ## Windows / Docker Desktop (WSL2)

  The WSL2 VM defaults to 50% of host RAM, with swap at 25% of that. Run
  17's VM (15.29 GiB, 4 GiB swap, no `.wslconfig`) ran mongod with no
  memory cap, exhausted its swap at 19:07:38Z and moved 121.4 GiB through
  it, which inflated the rebuild. With `swap=0` and the container cap
  above, an undersized configuration shows up as visible cache misses or
  an OOM kill instead — not as swap that silently masks the problem.

  1. Set `%UserProfile%\.wslconfig`:
     ```ini
     [wsl2]
     memory=<M + 2 GiB + anything else you run in the VM>
     swap=0
     ```
  2. `wsl --shutdown`, then restart Docker Desktop.
  3. Verify: `docker info --format "{{.MemTotal}}"` (should reflect the new
     `memory=` figure), and, inside the container,
     `docker exec <container> cat /proc/swaps` (should list no swap
     device — header line only).

  ## Watching a rebuild

  The automatic rebuild logs `deferred reindex generation started` at
  `info`, with `job_id`, `submission`, `manifest`, `types` and `resources`.
  It ends with `deferred reindex generation completed` (`info`),
  `deferred reindex generation was cancelled` (`warn`), or a `warn`/`error`
  failure line — all from `crates/persistence/src/search/reindex.rs`. Poll
  `GET /$reindex-status/{job_id}` with that `job_id` for `processed`/
  `total`, `entriesCreated` and `errorCount`.

  On the MongoDB side, sample
  `db.serverStatus().wiredTiger.cache["pages read into cache"]` and
  `db.serverStatus().opcounters.insert` a few minutes apart. The first
  counter is cumulative (it rises on every page read from disk, not only
  during a rebuild), so compare its **delta per inserted row** between two
  samples, not its absolute value. If that per-row figure keeps climbing
  while `processed` advances through your largest type, that type's slice
  has outgrown the cache.

  ## Restarts

  The MongoDB deferred rebuild is **not** resumed after a restart (#1283):
  if HFS restarts mid-rebuild, run `POST /{type}/$reindex` for every type
  listed in that generation's `types` field (the `deferred reindex
  generation started` line). You can also run `POST /$reindex` for those
  types. Reads and history are unaffected throughout — only search
  visibility for that type's resources is behind until the rebuild (or the
  manual `$reindex`) finishes.
  ````
